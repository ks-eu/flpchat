# Accounts, administration, configuration, whispers and history

Use the server's ordered session router as the foundation for authenticated identity and private delivery. Start configuration alongside [the current-code repairs](current.md). Implement accounts and whispers before durable message history. This roadmap assumes the necessary frames and identifier widths exist in `flpc`. The proposed command names and defaults are suggestions for Floppy.

## Readiness

| Feature | Reusable today | Missing before release |
| --- | --- | --- |
| Configuration | Listener address, capacity, queue sizes and client limits have identifiable consumers. | Typed startup settings, validation, and settings passed to the components that own them. |
| Persistent login | A framed handshake and a separate login window. | An account store, verified transport, credential UI, and a durable ID distinct from a connection token. |
| Administrator status | Central dispatch provides a place to check permissions. | Trusted role data and a local bootstrap path. Today any available username can be claimed. |
| Whispers | The server already has a writer per live user. | Safe recipient resolution across reconnects, a direct-delivery path, and private results for the sender. |
| History | Public messages already pass through a central router. The client bounds visible scrollback. | Durable identity, a recorded audience, commit acknowledgements, restart recovery, and participant-scoped history queries. |

## 1. Configuration and the account store

- **Load settings before startup.** Add separate `ServerConfig` and `ClientConfig` types backed by TOML. Accept `--config PATH`. Use built-in defaults when the option is omitted and report an explicitly missing or invalid file as a startup error. Resolve relative paths from the config file's directory. Report the offending setting for unknown keys, out-of-range values, invalid endpoints, or inaccessible files. Start with restart-to-apply behavior.
- **Give each setting an owner.** Server settings cover listen address, active and pending connection limits, handshake timeout, queue capacities, application input limits, database path, TLS certificate and private-key paths. Client settings cover server endpoint, certificate trust, and scrollback. Preserve the current loopback address and the working queue defaults. Validate capacities before constructing Tokio channels and enforce the protocol's byte ceilings. Store private keys in permission-restricted files. Keep account passwords out of configuration.
- **Separate durable accounts from live sessions.** Introduce distinct Rust types for a database-assigned `AccountId` and a fresh `SessionId` for each connection. Keep any compact wire identifiers in the protocol adapter. Use stable account IDs in permissions, whisper recipients and database relationships. Use session tokens for live routing and stale-command rejection.
- **Create a server-owned SQLite database.** Apply versioned migrations before accepting connections. Start with `accounts(id, username, username_key, password_hash, role, created_at)`, a unique canonical username key, and a role constrained to `user` or `admin`. Suggested first-release names use ASCII letters, digits and underscores, preserve display casing, and use lowercase for lookup. Let the unique constraint settle racing registrations. Disconnecting removes only the live session.
- **Keep the storage interface small.** Implement a concrete `AccountStore` for account creation, lookup and credential updates. Use bound SQL parameters, bounded database concurrency, and enable foreign keys for every connection. Keep disk waits and password hashing outside the session router. Report migration failures before opening the listener. The old server has no persistent identity to migrate, so deployment starts with a fresh account namespace. [SQLite foreign key guidance](https://www.sqlite.org/foreignkeys.html)

**Acceptance.** Start the server with valid defaults and a valid explicit config. Exercise invalid queue sizes, unknown settings, missing config, bad paths, and migration failure. Race equivalent registrations, restart, and verify that exactly one account retains the same ID, username and role.

## 2. Authentication and administrator status

1. **Secure the connection before requesting credentials.** Use TLS with server identity verification. Give a local deployment a documented way to configure a trusted local certificate. Surface certificate errors on the login screen. Reject legacy username-only joins once authentication is enabled. Release compatible client and server binaries together.
2. **Add explicit Register and Log in actions.** Collect the username and a masked password. Preserve the username on retry and clear the password after submission or cancellation. Exclude credentials from debug representations, message histories and logs. Give unknown users and incorrect passwords the same public login error. Bound concurrent handshakes, login attempts and concurrent hashing work.
3. **Persist password verifiers.** Generate a fresh salt per password and store an encoded Argon2id hash with its parameters. Start benchmarking at 19 MiB memory, two iterations and parallelism one. Bound admission to blocking hash workers before dispatching work. Verify existing hashes with their stored parameters and upgrade them after successful login when needed. [OWASP password storage guidance](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html)
4. **Establish the session after verification.** Load the account ID, username and trusted role, then ask the router to admit the account atomically. Default to one active session per account. Return the authenticated identity to the client and begin roster synchronization only after admission. Reject chat, whisper, history and administrative requests before authentication completes.
5. **Bootstrap the administrator locally.** Reserve the canonical name `root` in ordinary registration. Supply a local `server init-root` command that prompts privately for the password and transactionally creates the admin account. Repeated initialization preserves existing credentials. Provide an explicit local reset operation for recovery and require reauthentication of any existing root session after reset. Enforce each privileged operation server-side using the stored role. Show the role in the authenticated profile and roster. Ship administrative commands as their behavior is defined.

**Acceptance.** Exercise valid credentials, wrong passwords, unknown accounts, root case variants, private password entry, certificate verification failure, two concurrent logins, and a reconnect. Test bootstrap and reset across restarts. Assert that an ordinary user cannot gain privileges by supplying a role or spoofing a name. A rejected client receives no roster, history or chat content.

## 3. Live whispers

- Add distinct commands for a public message and a whisper. Parse `/w <username> <text>` in the chat UI. Preserve a malformed command in the editor with a visible error. Resolve the target's canonical username on the server and derive the sender from the authenticated connection.
- Add direct delivery to the router. Resolve the stable target account to its current session, verify that it is still active, then enqueue to that session's writer. Return a private outcome to the sender. Keep whisper events out of the public fan-out path, including error handling. Give self-whispers one visible copy.
- Add distinct UI events for an incoming whisper, an accepted outgoing whisper, and failure. Display the peer and direction even if the peer leaves the roster immediately afterward. Initially deliver only to online recipients. Report offline, unavailable or evicted recipients privately. An acceptance at this phase means the recipient's server-side queue accepted the event. Keep message bodies out of operational logs.

**Acceptance.** Connect Alice, Bob and Carol. Verify the exact frames each receives when Alice whispers to Bob. Repeat with Carol as administrator, Bob disconnecting during delivery, a full target queue, an unknown target, a malformed command, a self-whisper and a stale request from an earlier session. Assert zero public copies in every case.

## 4. Persist room messages and whispers

1. **Migrate the schema.** Add `messages` with an ordered server-assigned message ID, sender account ID, nullable recipient account ID, kind, body, server timestamp and client submission ID. Use foreign keys and checks tying a public message to an empty recipient and a whisper to a valid recipient. Make the pair of sender ID and submission ID unique. Index public history by message ID and private history by sender, recipient and message ID.
2. **Acknowledge after commit.** Give the client a fresh submission ID for each intentional send and reuse it on retry. Pass the authenticated request to a bounded persistence worker. Serialize committed delivery in message-ID order. Commit before acknowledging the sender or broadcasting to peers. A retry with identical content returns the original message ID and produces no second broadcast. Reject a reused ID with changed content or audience. A failed commit yields a private failure and retains the draft. A crash after commit is recoverable through history. Replace the current unconditional local echo with a pending entry reconciled by acknowledgement.
3. **Authorize every history query.** Provide separate bounded queries for public history and a conversation with one peer. Derive the requesting account from the session. Filter whispers to the two directions between that account and the selected peer in SQL before ordering and pagination. Apply this restriction to administrators as well. Render the author from account data even when they are offline. Database files and backups contain private message bodies and need restricted access.
4. **Join history to live traffic.** Register the live subscription and obtain a committed high-water message ID at an ordered boundary. Page the snapshot up to that ID and merge buffered live events using server message IDs. Fetch older pages with an exclusive cursor, display each page chronologically, and retain bounded client scrollback. On reconnect, request the gap since the last seen ID for the authorized view. If live buffering overflows, resynchronize from the last confirmed cursor.
5. **Enable offline whispers once storage is authoritative.** Accept a whisper to an existing offline account after commit and report it as stored. Make it discoverable on reconnect through a participant-scoped conversation list with peer and latest message ID. Use the same authorization predicate for the list and the conversation contents. A read receipt would require a separate recipient action.
6. **Roll out and recover.** Default to indefinite retention and document that choice for operators. Perform an SQLite-consistent backup before upgrading an existing account database. Test restoration into a fresh instance and rehearse rollback with a matching backup and binary. Keep transient presence events out of message history.

**Acceptance.** Test restart recovery, write failure, crash after commit, retries with a lost acknowledgement, overlapping history and live delivery, equal timestamps, narrow page boundaries, a recipient disconnecting after commit, and retrieval while the author is offline. Verify that third parties and administrators cannot retrieve or enumerate other users' whisper conversations. A restore drill must recover accounts, roles, public history and private conversations together.

## Delivery gates

Land configuration and session fixes independently. Ship authenticated accounts and root provisioning together, then online whispers, then durable history and offline delivery. At each gate, run workspace format, strict Clippy, tests, and the phase's acceptance scenarios. Before the authentication cutover, tell operators how to initialize root, configure trust, and start the matching client. Before the storage cutover, document the change from queue acceptance to durable acknowledgement and the retention policy for private messages.
